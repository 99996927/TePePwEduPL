# Plan 5: `Hr.Agent` — agent AI, narzędzia, Kodeks pracy, historia rozmów — plan implementacji

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Dodać agenta AI (Anthropic API, tool use), który odpowiada na pytania o urlop, nadgodziny i przepisy Kodeksu pracy oraz przygotowuje dla kadr szkice korekt ewidencji, wywołując wyłącznie narzędzia z `Hr.Core` (agent nigdy nie liczy sam). Rozmowy są zapisywane w całości i udostępniane przez API (UC-21 do UC-27, UC-30, UC-31). Sednem planu jest **wyzwanie projektu**: deterministyczny silnik reguł (w tym płacowych), który agent wywołuje przez narzędzia, ale którego wyników nigdy nie zastępuje własnymi obliczeniami.

**Architecture:** Nowy projekt `Hr.Agent` zależy tylko od `Hr.Core` i korzysta wyłącznie z przestrzeni nazw `Hr.Core.AgentTools` (interfejsy `IAgentToolbox`, `IConversationStore`; wyniki narzędzi to gotowy JSON, więc agent nie widzi typów `Hr.Rules` ani `DbContext`). Narzędzia i magazyn rozmów są zaimplementowane w `Hr.Core` w kontekście zalogowanego użytkownika (`ICurrentUser`), więc zakres danych egzekwują serwisy z planu 3. `Hr.Agent` jest zbudowany na **oficjalnym SDK Anthropic dla C#** (pakiet `Anthropic`, adapter `IChatClient`) i abstrakcjach agentowych `Microsoft.Extensions.AI`: narzędzia z `Hr.Core` są rejestrowane jako `AIFunction`, a pętlę „model → narzędzie → model” prowadzi `FunctionInvokingChatClient` (SDK), a nie nasz kod HTTP. Nasz kod to cienkie warstwy: adapter narzędzi, ochrona przed awarią modelu (`DelegatingChatClient`), `AgentRunner` (historia, zapis, korekta) i osłona liczb (`NumberGuard`). W testach model jest skryptowanym `IChatClient`, ale pętla narzędzi jest prawdziwa. Tekst Kodeksu pracy jest importowany jednorazowo skryptem do pliku JSON w repozytorium i ładowany do bazy przy starcie.

**Tech Stack:** .NET 9, oficjalne SDK `Anthropic` (NuGet, v10+, wymaga .NET Standard 2.0+), `Microsoft.Extensions.AI` (`IChatClient`, `AIFunction`, `UseFunctionInvocation`), EF Core 9, xUnit, NetArchTest, Testcontainers.MsSql; skrypt importu w Pythonie 3 z `pypdf` (tylko narzędzie deweloperskie, poza rozwiązaniem .NET).

**Spec:** `docs/arc42/README.md` (sekcje 3.5 UC-21..27, 30, 31; 5.4; 6.3, 6.5; 8.2, 8.3a; 9: ADR-04, 05, 09, 11, 12, 14, 24, 25; 10: Q-04, Q-05, Q-07, Q-08; 11: R-01, R-04, R-06, R-07, R-10). Poprzednie plany (zmergowane): 1 (silnik), 2 (dane), 3 (serwisy), 4 (API). Kolejne: dane demo, Angular, Docker, E2E.

## Global Constraints

- `net9.0`, `Nullable` włączone, ostrzeżenia jako błędy. `Hr.Agent` referencjonuje wyłącznie `Hr.Core`; używa tylko typów z `Hr.Core.AgentTools` (test architektury). `Hr.Core` nie zna `Hr.Agent`. `Hr.Rules` pozostaje bez zmian.
- Liczby w odpowiedzi agenta pochodzą wyłącznie z wyników narzędzi (ADR-04). Tożsamość użytkownika pochodzi z sesji, nie od modelu: parametr `employee_id` jest honorowany tylko dla `HR` i `HRApprover` (i nadal przechodzi przez zakres danych serwisów); dla pozostałych narzędzia działają na własnych danych i parametr jest ignorowany.
- **Agent nie liczy:** żadna kwota, liczba godzin ani dni nie powstaje w modelu. Pytania o wynagrodzenie obsługuje narzędzie `get_payroll_result`, które tylko **czyta** naliczenie wykonane wcześniej przez silnik (`PayrollService.GetAsync`); agent nie uruchamia naliczeń (to czynność kadr), a gdy naliczenia brak, odpowiada, że nie zostało jeszcze wykonane, i nie szacuje kwoty. Obejście przez model (szacowanie, sumowanie, przeliczanie stawek) jest wykrywane przez `NumberGuard` i wymuszane do poprawki (Task 8).
- Narzędzia agenta nie zmieniają danych źródłowych. Jedyny zapis to szkic korekty wpisu czasu (`propose_correction`, status „oczekuje”), a zmiana stawek i składników wynagrodzenia nie jest dostępna dla agenta (ADR-15).
- Wynik narzędzia to JSON `camelCase`; błąd to `{"error":{"code":"NotFound|Forbidden|Validation|Conflict|UnknownTool|InvalidInput","message":"…","ruleId":"…"}}` i jest przekazywany modelowi jako `is_error: true` (UC-25: agent nie zgaduje liczby).
- **Agent na SDK:** żadnego ręcznego klienta HTTP ani ręcznej pętli narzędzi. Model przez `AnthropicClient.AsIChatClient(model)`, pętla narzędzi przez `UseFunctionInvocation()` z `MaximumIterationsPerRequest = 6`, narzędzia jako `AIFunction`. Wersje pakietów: najnowsze **stabilne** z NuGet.org (bez wersji `custom`/niestandardowych wydań), wpisane na stałe w `.csproj`; jeśli oficjalny pakiet `Anthropic` nie ma stabilnej wersji ≥ 10 albo jego API różni się od opisanego w planie, wykonawca zatrzymuje się i zgłasza to zamiast improwizować.
- Klucz API tylko z konfiguracji (`Anthropic:ApiKey` lub zmienna `ANTHROPIC_API_KEY`, którą SDK czyta sam), nigdy z repozytorium. Model z `Anthropic:Model` (domyślnie `claude-sonnet-5-5`). Brak klucza lub błąd sieci/429/5xx (po wewnętrznych ponowieniach SDK: `MaxRetries = 2`) → `503` z `code=AgentUnavailable`; reszta systemu działa (Q-05).
- Odpowiedź w całości, bez strumieniowania (ADR-14; wywołanie `GetResponseAsync`). Maksymalnie 6 rund narzędzi na jedno pytanie, pytanie do 4000 znaków, kontekst z ostatnich 40 wiadomości rozmowy.
- Rozmowa należy do autora (`Conversation.UserId`); autor czyta swoje, `HR` i `HRApprover` czytają wszystkie (odczyt cudzej zapisuje `ConversationRead`, `ConversationReader` z planu 2), pozostali dostają 404 (ADR-11).
- Konwencja zapisu wiadomości (`Message`): `User`/`Assistant` — `Content` to tekst; `ToolCall` — `Content` to identyfikator `tool_use`, `ToolName`, `ToolParamsJson` to parametry; `ToolResult` — `Content` to JSON wyniku, `ToolName` nazwa narzędzia. Wywołanie i jego wynik są zapisywane parami, w kolejności wykonania.
- Konwencje API jak w ADR-25 (ProblemDetails z `code`, kody 404/403/422/409, antyforgery, brak sesji → 401). Nazwy testów zaczynają się od `UCxx_` albo opisują kontrakt. Komunikaty commitów po polsku, w formie rozkazującej, bez emoji.
- Testy integracyjne na SQL Server w kontenerze (`DOCKER_API_VERSION=1.43`); testy agenta bez sieci i bez klucza (skryptowany `IChatClient`, ale z prawdziwą pętlą narzędzi SDK).

## Review Focus

1. **Model zmyśla narzędzie albo przysyła niepoprawne parametry:** nieznana nazwa lub zły JSON daje wynik błędu `UnknownTool`/`InvalidInput`, pętla trwa dalej i nic się nie wywraca (Task 5, 8).
2. **Model zapętla się w wywołaniach narzędzi:** po 6 rundach agent przerywa i zwraca komunikat zastępczy, rozmowa pozostaje spójna (Task 8).
3. **Wstrzyknięcie poleceń / próba odczytu cudzych danych (UC-24, R-07):** pracownik, który każe modelowi użyć cudzego `employee_id`, nie dostaje danych, bo parametr jest ignorowany; kierownik nie dostaje danych spoza zespołu (Task 4).
4. **Awaria Anthropic (timeout, 429, 5xx, brak klucza):** `503 AgentUnavailable`, pytanie zostaje w historii; wywołania narzędzi wykonane przed awarią są zapisane jako kompletne pary (nigdy samo wywołanie bez wyniku), więc kolejne pytanie nie dostaje zepsutej historii (Task 7, 8, 9).
5. **Liczba w odpowiedzi spoza wyników narzędzi (R-01, Q-04, wyzwanie projektu):** model sam szacuje lub przelicza kwotę albo godziny (np. „około 5000 zł brutto”, suma dwóch wyników). `NumberGuard` to wykrywa, runner raz wymusza poprawkę, a jeśli liczba zostaje, API zwraca ostrzeżenie `ungroundedNumbers` zapisane w audycie (Task 8, 9).
6. **Pytanie o wynagrodzenie bez wykonanego naliczenia:** agent nie podaje kwoty, tylko informuje, że naliczenia brak (Task 5, 9).
